# دعم بيع المنتجات بالكرتونة — مواصفة التصميم

- **التاريخ:** 2026-08-09
- **الحالة:** معتمد — جاهز لخطة التنفيذ
- **النطاق:** الباك‌إند فقط (NestJS + Prisma). الواجهة مشروع منفصل.

---

## ١. الخلفية

المتجر بيشتري منتجات بالكرتونة وبيبيعها بالقطعة أو بالكرتونة. حالياً النظام بيعرف وحدة واحدة بس (القطعة)، فالكاشير مضطر يحسب بإيده كم قطعة في الكرتونة وقت الإدخال، وما في طريقة يبيع كرتونة كاملة بسعرها الخاص.

**القيد الحاكم:** الموقع شغّال على البرودكشن وعليه بيانات حقيقية (منتجات، فواتير، ديون). أي تغيير لازم يكون إضافة صرفة — ولا صف موجود بينكتب عليه، ولا مسار حالي بينكسر.

---

## ٢. المبادئ الحاكمة

1. **الميجريشن إضافة فقط.** `ADD COLUMN` و `CREATE TYPE` بس. ممنوع `UPDATE` أو `DROP` أو `SET NOT NULL` على بيانات موجودة.
2. **كل الحقول الجديدة اختيارية.** طلب قديم بدون أي حقل جديد لازم يشتغل بنفس السلوك الحالي حرفياً.
3. **ما نثق بأرقام الواجهة.** أسعار الكرتونة وحجمها بتنقرأ من صف المنتج في قاعدة البيانات، مش من الطلب.
4. **لقطة تاريخية.** سطر الفاتورة بيخزّن سعره وتكلفته وكمية الخصم وقت البيع، فتغيير بيانات المنتج بعدين ما بيأثر على فاتورة قديمة.
5. **المخزون دايماً بالقطع.** `Product.stock` أبداً ما بينخزن بالكراتين.

## ٣. قاعدة البيانات

### ٣.١ جدول `products` — ٣ أعمدة جديدة

```prisma
piecesPerCarton     Int?
cartonPurchasePrice Decimal? @db.Decimal(10, 2)
cartonSalePrice     Decimal? @db.Decimal(10, 2)
```

كلها `NULL`. كل منتج موجود حالياً بيصير `NULL` = "مش منتج كرتونة" بدون أي كتابة عليه.

### ٣.٢ نوع جديد

```prisma
enum SaleUnit {
  UNIT
  CARTON
}
```

### ٣.٣ جدول `invoice_items` — عمودين جدد

```prisma
saleUnit      SaleUnit @default(UNIT)
stockQuantity Int?
```

**ليش هالشكل بالذات:**

| العمود | القرار | السبب |
|---|---|---|
| `saleUnit` | `NOT NULL DEFAULT 'UNIT'` | القيمة الافتراضية ثابتة، فبوسطجرس ١١+ الإضافة metadata-only — فورية وبدون إعادة كتابة الجدول. كل الفواتير القديمة بترجع `UNIT` تلقائياً. صفر كتابة. |
| `stockQuantity` | `NULL` مع fallback في الكود | القيمة الصحيحة تاريخياً هي `quantity` وهي **مختلفة لكل صف**، فما بتنعبر بقيمة افتراضية ثابتة. البديل (`UPDATE` على كل الفواتير القديمة) بيلمس بيانات البرودكشن — مرفوض. الكود بيقرأ `stockQuantity ?? quantity`. |

### ٣.٤ الميجريشن المتوقع

```sql
CREATE TYPE "SaleUnit" AS ENUM ('UNIT', 'CARTON');

ALTER TABLE "products"      ADD COLUMN "piecesPerCarton"     INTEGER;
ALTER TABLE "products"      ADD COLUMN "cartonPurchasePrice" DECIMAL(10,2);
ALTER TABLE "products"      ADD COLUMN "cartonSalePrice"     DECIMAL(10,2);

ALTER TABLE "invoice_items" ADD COLUMN "saleUnit"      "SaleUnit" NOT NULL DEFAULT 'UNIT';
ALTER TABLE "invoice_items" ADD COLUMN "stockQuantity" INTEGER;
```

كلها فورية. النشر بيمرّ على `prisma migrate deploy` الموجود في سكربت `start:migrate`.

## ٤. المنتج — إنشاء (`POST /products`)

### ٤.١ حقول `CreateProductDto` الجديدة (كلها اختيارية)

| الحقل | النوع | تحقّق | بينخزن؟ |
|---|---|---|---|
| `piecesPerCarton` | `Int` | `Min(1)` | ✅ |
| `cartonPurchasePrice` | `Decimal(10,2)` | `Min(0)` | ✅ |
| `cartonSalePrice` | `Decimal(10,2)` | `Min(0)` | ✅ |
| `cartonCount` | `Int` | `Min(0)` | ❌ — للحساب وقت الإنشاء بس |

### ٤.٢ قاعدة "يا كلهم يا ولا واحد"

الحقول الثلاثة `piecesPerCarton` / `cartonPurchasePrice` / `cartonSalePrice` إما كلهم موجودين أو كلهم غايبين. أي حالة بينهم → `400` برسالة عربية واضحة.

**السبب:** منتج فيه عدد قطع وسعر شراء بدون سعر بيع كرتونة بيظهر في الواجهة كمنتج كرتونة، بس أول محاولة بيع كرتونة بترفض. بيانات ناقصة صامتة بتنكشف بعد أسبوع مش وقت الإدخال.

`cartonCount` بدون `piecesPerCarton` → `400` كمان (ما إله معنى لحاله).

### ٤.٣ الحساب في وضع الكرتونة

```
stock          = (cartonCount ?? 0) × piecesPerCarton + (dto.stock ?? 0)
wholesalePrice = cartonPurchasePrice ÷ piecesPerCarton      ← يتجاهل المرسل
price          = dto.price                                   ← من المستخدم زي ما هو
```

**خانة "الكمية" (`stock`) في وضع الكرتونة معناها "قطع فرط إضافية"** وبتنجمع فوق قطع الكراتين. هاد انحراف مقصود عن التقرير الأصلي — بند ١١.

مثال: `2 كرتونة × 24 قطعة + 5 فرط = 53 قطعة` · `48 ÷ 24 = 2.00 شيكل للقطعة`

القسمة بتقرّب لمنزلتين (حدود عمود `Decimal(10,2)`).

### ٤.٤ بدون حقول كرتونة

السلوك الحالي حرفياً. ولا سطر منطق جديد بينفّذ.

---

## ٥. المنتج — تعديل (`PATCH /products/:id`)

- بيقبل الحقول الثلاثة → عشان يقدر المتجر يحوّل منتجاته الموجودة على البرودكشن لمنتجات كرتونة.
- **ما بيقبل `cartonCount`.** المخزون أبداً ما بينعاد حسابه من عدد الكراتين عند التعديل، لأن قطع منه ممكن تكون انباعت.
- لو تغيّر `cartonPurchasePrice` أو `piecesPerCarton` والمنتج بعد التعديل عنده بيانات كرتونة كاملة → `wholesalePrice` بينعاد حسابه (نفس معادلة الإنشاء).
- إرسال `null` للحقول الثلاثة بيلغي وضع الكرتونة.
- قاعدة "يا كلهم يا ولا واحد" بتتحقق على **الحالة النهائية** بعد الدمج مع الصف الموجود، مش على الطلب لحاله.

تغيير `piecesPerCarton` بعد بيع كراتين آمن: كل سطر فاتورة قديم عنده `stockQuantity` الخاص فيه.

## ٦. الفاتورة — إنشاء (`POST /invoices`)

### ٦.١ الحقل الجديد

`CreateInvoiceItemDto.saleUnit?: 'UNIT' | 'CARTON'` — غايب = `UNIT`.

### ٦.٢ اشتقاق قيم السطر

| | `UNIT` (أو غايب) | `CARTON` |
|---|---|---|
| `price` | `product.price` | `product.cartonSalePrice` |
| `unitCost` | `product.wholesalePrice` | `product.cartonPurchasePrice` |
| `quantity` | كما أُرسل | كما أُرسل (عدد كراتين) |
| `stockQuantity` | `quantity` | `quantity × product.piecesPerCarton` |
| `total` | `price × quantity` | `price × quantity` |

كل القيم من صف المنتج في قاعدة البيانات. الواجهة ما بتبعت ولا سعر.

### ٦.٣ التحقق

`saleUnit: CARTON` على منتج ناقص أي من `piecesPerCarton` / `cartonSalePrice` / `cartonPurchasePrice` → `400` برسالة عربية تسمّي المنتج.

### ٦.٤ خصم المخزون

الخصم الشرطي الذرّي الموجود حالياً بيستخدم `stockQuantity` بدل `quantity`. رسالة "الكمية تتجاوز المخزون" لازم تعرض **القطع** لا الكراتين — وإلا بتطلع رسالة مثل «الكمية المطلوبة (1) تتجاوز المخزون المتوفر (20)» وهي مربكة للمستخدم.

### ٦.٥ قطع وكراتين من نفس المنتج بنفس الفاتورة

بيشتغل تلقائياً — سطرين مستقلين، كل واحد بـ `stockQuantity` الخاص فيه، والخصم بيمرّ عليهم بالتتابع داخل نفس الترانزاكشن.

---

## ٧. الفاتورة — تعديل وحذف

- **تعديل:** إرجاع مخزون البنود القديمة بـ `stockQuantity ?? quantity`، وخصم البنود الجديدة بنفس منطق الإنشاء.
- **حذف:** إرجاع المخزون بـ `stockQuantity ?? quantity`.

الـ `?? quantity` هي اللي بتخلي فواتير ما قبل الميجريشن (`stockQuantity = NULL`) ترجع مخزونها صح بالظبط زي قبل.

**قوائم `select` لازم تضيف `stockQuantity`** في `invoice.update` و `invoice.remove` — بدونها الكود بيقرأ `undefined` وبيرجع مخزون غلط بصمت.

---

## ٨. الاستجابات

إضافة `saleUnit` و `stockQuantity` لقوائم حقول البنود في:

- `GET /invoices/:id`
- `GET /invoices/number/:number`
- `GET /customers/:id` (سجل فواتير العميل)

مسارات الإنشاء والتعديل بتستخدم `include: { items: true }` فبترجعهم تلقائياً.

## ٩. المزامنة الأوف‌لاين (`POST /sync/push`)

هاد المسار بيخصم المخزون بشكل مستقل تماماً عن `invoice.service` — بدون تغطيته، أي كرتونة تنباع والجهاز مقطوع نت بتخصم قطعة واحدة بدل كرتونة كاملة، والمخزون بينحرف بصمت.

`SyncInvoiceItemDto` بياخد `saleUnit?` و `stockQuantity?`. كمية الخصم:

```
stockQuantity المرسل
  ?? (saleUnit === CARTON && product.piecesPerCarton
        ? quantity × product.piecesPerCarton
        : quantity)
```

`piecesPerCarton` بينجاب ضمن استعلام التحقق من ملكية المنتجات الموجود أصلاً (بدون round-trip زيادة).

**لو أجا `CARTON` والمنتج ما إله بيانات كرتونة:** تحذير في اللوج والخصم بالقطعة — **بدون رفض الفاتورة**. البيعة صارت فعلاً على الأرض ورفضها بيضيّعها نهائياً. نفس فلسفة الموديول الحالية مع انحراف المخزون.

---

## ١٠. التقارير — لا تغيير

تحقّق على `reports.service.ts`:

- الإيراد = `SUM(invoice_items.total)`، و `total = price × quantity`. لسطر كرتونة: سعر الكرتونة × عدد الكراتين ✅
- التكلفة = `SUM(unitCost × quantity)`. لسطر كرتونة: تكلفة الكرتونة × عدد الكراتين ✅

الأرقام صحيحة بدون أي تعديل، لأن `price` و `unitCost` مخزّنين بنفس الوحدة اللي `quantity` مقاسة فيها. `_sum.quantity` بينحسب داخلياً بس ما بينرجع في الاستجابة، فما في نتيجة جانبية.

## ١١. قرارات مقصودة وانحرافات عن التقرير الأصلي

| # | التقرير قال | القرار | السبب |
|---|---|---|---|
| ١ | `stock = cartonCount × piecesPerCarton` | `+ الكمية المرسلة` كمان | قرار المالك: خانة "الكمية" بتضل في الفورم وبتستخدم للقطع الفرط. **لازم مطور الفرونت يعرف.** |
| ٢ | لم يذكر المزامنة الأوف‌لاين | ضمن النطاق | ثغرة مخزون حقيقية في تطبيق PWA فيه وضع أوف‌لاين. |
| ٣ | «حمّل بيانات المنتج داخل معاملة واحدة» | جلب المنتجات بيضل قبل الترانزاكشن | الهدف الأمني (ما نثق بأرقام الواجهة) متحقق ١٠٠٪. النقل جوّا الترانزاكشن معناه إعادة هيكلة دالة إنشاء الفاتورة كاملة — أخطر تغيير ممكن على كود شغّال. الكمية المخصومة هي بالظبط الكمية المخزّنة، فما في تعارض ممكن ينتج. |

## ١٢. ملاحظات لمطور الواجهة

1. **"الكمية" في وضع الكرتونة = قطع فرط إضافية، بتنجمع فوق قطع الكراتين.** المالك مصرّ يخلي الخانة زي ما هي. خطر معروف: كاشير بيدخل ٤٨ في الخانة قاصد المخزون الكلي فيصير المخزون ٩٦. تسمية أوضح للخانة بتقلل الخطر.
2. **"سعر الجملة" بينتجاهل في وضع الكرتونة** — يفضّل يكون مخفي أو `readonly` محسوب، وإلا الكاشير بيكتب رقم وبينحفظ رقم ثاني.
3. `stock` في كل الاستجابات دايماً **بالقطع**، أبداً بالكراتين.
4. الحقول الثلاثة بتنبعت مع بعض أو ما تنبعت أبداً.
5. طابور الأوف‌لاين (outbox) لازم يبعت `saleUnit` مع كل سطر كرتونة، ويفضّل يبعت `stockQuantity` كمان.

---

## ١٣. خارج النطاق (YAGNI)

- باركود مستقل للكرتونة.
- زيادة المخزون بالكراتين عند التعديل («وصلني ٣ كراتين») — إعادة تخزين بتحتاج مسار خاص فيها.
- عرض المخزون بصيغة «٢ كرتونة و٥ قطع» في الاستجابة — الواجهة بتقدر تشتقها من `stock` و `piecesPerCarton`.
- تنبيه المخزون المنخفض بالكراتين — `minStock` بيضل بالقطع.

## ١٤. معايير القبول

**توافق خلفي (الأهم):**
1. إنشاء منتج بدون أي حقل كرتونة → نفس السلوك الحالي بالظبط.
2. إنشاء فاتورة بدون `saleUnit` → نفس السلوك الحالي، الخصم بالقطعة.
3. تعديل/حذف فاتورة **أُنشئت قبل الميجريشن** → المخزون بيرجع صح (مسار `?? quantity`).
4. تقرير الأرباح لفواتير قديمة → نفس الأرقام قبل وبعد الميجريشن.

**وظائف جديدة:**
5. منتج بـ `piecesPerCarton: 24`, `cartonCount: 2`, `stock: 5` → `stock = 53`.
6. نفس المنتج بـ `cartonPurchasePrice: 48` → `wholesalePrice = 2.00`.
7. بيع كرتونة واحدة → المخزون بينقص ٢٤، والسطر بيخزّن `saleUnit: CARTON`, `stockQuantity: 24`, `price = cartonSalePrice`.
8. بيع كرتونة + ٣ قطع من نفس المنتج بنفس الفاتورة → سطرين، الخصم الكلي ٢٧.
9. بيع كرتونة والمخزون ٢٠ قطعة بس → `400` والرسالة بتذكر ٢٤ و ٢٠ (بالقطع).
10. `saleUnit: CARTON` على منتج عادي → `400`.
11. حذف فاتورة فيها سطر كرتونة → المخزون بيرجع ٢٤ مش ١.
12. مزامنة أوف‌لاين لفاتورة فيها كرتونة → الخصم ٢٤.

**تحقّق:**
13. إرسال `piecesPerCarton` بدون `cartonSalePrice` → `400`.
14. `cartonCount` بدون `piecesPerCarton` → `400`.
15. تعديل منتج بإرسال `cartonCount` → الحقل بينتجاهل، المخزون ما بيتغيّر.
